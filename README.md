# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователь способен включать и выключать отопление в доме.
- Система поддерживает добавление/удаление и обновление информации о сенсорах

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах
- Система поддерживает получение информации о температуре по Id Сенсора или Id локации

Сервис sensors имеет следующие ручки
```
GET /sensors - Получить список всех датчиков
GET /sensors/:id - Получить конкретный датчик по ID
POST /sensors - Создать новый датчик
PUT /sensors/:id - Полное обновление датчика
DELETE /sensors/:id - Удалить датчик
PATCH /sensors/:id/value - Обновить показания датчика
GET /sensors/temperature/:location - Получить температуру по местоположению
```

### 2. Анализ архитектуры монолитного приложения

Перечислите здесь основные особенности текущего приложения: какой язык программирования используется, какая база данных, как организовано взаимодействие между компонентами и так далее.

* **Язык программирования:** Go
* **База данных:** PostgreSQL
* **Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.

Сервис sensors не имеет чётко определённой зоны ответственности:
1. В коде явно не показано, как осуществляется взаимодействие с физическими датчиками. По имеющимся предположениям:
   - Пользователь через пользовательский интерфейс инициирует запрос к сервису sensors на изменение состояния устройства (например, температуры или питания);
   - Сервис sensors обрабатывает запрос, вызывая соответствующий хендлер;
   -Обработчики запросов на чтение обращаются к temperature-api, тогда как обработчики, изменяющие состояние, вероятно, воздействуют на устройство через специализированный API и одновременно вносят изменения в базу данных Sensors.
2. Модели данных недостаточно информативны:
   - В коде отсутствует явная связь между сущностью sensor и владельцем устройства (например, через home_id, обозначающий дом или квартиру пользователя);
   - Поле location ассоциировано с sensor_id и фактически выступает в роли его псевдонима;
   -Отсутствие home_id затрудняет понимание того, как сервис sensors идентифицирует устройство при запросе на изменение его состояния. Предполагается, что location служит инкапсуляцией, связывающей идентификатор дома пользователя и конкретную зону, в которой установлен сенсор. Например: /user/100/home/220/location/kitchen.

### **4. Проблемы монолитного решения**

* **Ограниченная масштабируемость**. "Агрессивный" мониторинг температуры может требовать больше ресурсов для
  выполнения агрегированных запросов. В это же время управление устройствами от пользователя явление не частое:
  установка либо демонтаж сенсора - запросы, которые можно рассчитывать не в пределах секунд, а в месяцах. Редактирование состояния сенсора - в пределах дня. 
* **Синхронное взаимодействие**, запросы обрабатываются последовательно.
* **Развертывание**: Требует остановки всего приложения.

# Задание 4. Создание и документирование API

### 1. Тип API

С учётом текущих условий и имеющихся данных, в архитектуре as-is будет использоваться синхронный API.
1. Сервис DeviceManager будет предоставлять ручки для управления устройствами, их состоянием и отправки команд. Для обеспечения плавного перехода от монолитной архитектуры к микросервисной, DeviceManager будет выполнять следующие функции:
- Интеграция с сервисом sensor для добавления и отвязки устройств. В текущей версии поддерживаются только температурные датчики.
 -Интеграция с сервисом sensor для управления состоянием устройств, включая изменение температурного режима и питания.
- Получение информации об устройствах также будет осуществляться через взаимодействие с сервисом sensor.
2. Сервис `Telemetry` будет отвечать за получение метрик с устройств. Его поведение включает:
- При переходе к микросервису возникает проблема: `Telemetry` должен иметь доступ к актуальному списку устройств. В связи с этим он будет использовать общую с DeviceManager базу данных, но только в режиме чтения. Более корректным архитектурным решением было бы внедрение event bus, через которую сервис получал бы события о добавлении и удалении устройств, сохраняя их в собственной базе.
- Сервис Telemetry запускает фоновый процесс, который периодически опрашивает temperature-api и сохраняет метрики в оперативной памяти (до тех пор, пока не будет подключено постоянное хранилище).

Синхронный API подходит как временное решение до полной миграции старой версии API к новой: пользователей сервиса не так много + крайне редкие изменения в SensorsDB.
Как было указано на диаграмме, постепенно по ходу введения новых типов устройств (в частности те, которые управляются командами) будут отправлять команды и изменение
состояния через событийную шину. Внтуренний сервис драйвера устройств должен обрабатывать очередь и применять команды. Таким образом DeviceManager не будет рисковать
обрабатывать запросы с долгими задержками, а также возможен вариант для сервиса Telemetry обращаться к списку устройств через контроллер Devices сервиса DeviceManager
если "мутирующая" нагрузка окажется не слишком большой.
